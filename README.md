# Асистент техпідтримки — стартовий код практичних

Стартовий код до практичних робіт курсу «Впровадження систем генеративного штучного інтелекту». Від практичної до практичної ви будуєте одного асистента техпідтримки умовного онлайн-сервісу бухгалтерського обліку для ФОП, тож і репозиторій у вас один на весь курс.

Цей репозиторій для вашого — `upstream`: джерело, з якого ви один раз берете код, а потім забираєте оновлення. Так само команди працюють із кодом, який супроводжує хтось інший. Кожна практична виходить тут новим релізом у гілці `main`: він додає каркас і матеріали наступного кроку, а ваш код лишається вашим. Умови, вимоги варіантів, критерії приймання й рубрики — в умовах практичних у матеріалах курсу.

## Практичні

| Практична | Опис | Реліз |
| --- | --- | --- |
| ПР2. Мінімальний асистент зі структурованим виходом | [`docs/triage.md`](docs/triage.md) | `practical/triage` |
| ПР3. RAG над базою знань компанії | [`docs/knowledge-base.md`](docs/knowledge-base.md) | `practical/knowledge-base` |

Що саме додав реліз, показує порівняння двох тегів на GitHub або `git diff <тег> <тег> --stat`.

## Як почати (один раз)

1. Установіть [git](https://git-scm.com/downloads) і [uv](https://docs.astral.sh/uv/getting-started/installation/). Потрібної версії Python uv завантажить сам.
2. Клонуйте цей репозиторій разом з історією:

   ```bash
   git clone --origin upstream https://github.com/pseudochaos/support-assistant-starter.git support-assistant
   cd support-assistant
   ```

   `--origin upstream` дає цьому репозиторію ім'я `upstream`, а ім'я `origin` лишає для вашого.
3. Створіть на GitHub порожній **приватний** репозиторій — без README, `.gitignore` і ліцензії — і надішліть у нього код:

   ```bash
   git remote add origin https://github.com/<ваш-логін>/support-assistant.git
   git push -u origin main
   ```

   З [GitHub CLI](https://cli.github.com/) це одна команда: `gh repo create support-assistant --private --source . --remote origin --push`.

   Не створюйте репозиторій кнопкою **Fork** — форк публічного репозиторію не можна зробити приватним, — і не завантажуйте ZIP: без спільної історії наступна практична не зіллється з вашим кодом.
4. Отримайте ключ Gemini API в [Google AI Studio](https://aistudio.google.com/apikey) за [інструкцією Google](https://aistudio.google.com/docs/api-key). Скопіюйте `.env.example` у `.env` і впишіть ключ у `GOOGLE_API_KEY`. Файл `.env` у git не потрапляє: так задано в `.gitignore`, не змінюйте цього.
5. Перевірте, що все працює:

   ```bash
   uv run pytest                          # тести без мережі й ключа
   uv run assistant "Як скинути пароль?"  # у каркасі: handle() is not implemented yet
   ```

Далі — опис практичної в `docs/` за таблицею вище.

## Наступна практична

Коли виходить наступна практична, закомітьте свою роботу і злийте `main` цього репозиторію зі своїм кодом:

```bash
git fetch upstream
git merge --no-edit upstream/main
git push
```

Команди ті самі для кожної практичної. Ними ж приходять виправлення в матеріалах курсу, якщо вони знадобляться посеред практичної. Саме `fetch` і `merge`, а не `git pull upstream main`: на гілках, що розійшлися, `pull` без додаткових налаштувань зупиняється з помилкою.

Злиття додає файли курсу і не змінює вашого коду. Нові змінні для `.env` злиттям не приходять, бо `.env` у git немає: їх перелічує опис практичної в `docs/`.

## Якщо злиття зупинилося на конфлікті

Конфлікт означає, що той самий файл змінили і ви, і курс. `git status` показує, які це файли; для кожного — свій рецепт:

| Файл | Що зробити |
| --- | --- |
| `pyproject.toml` | відкрийте файл, залиште рядки обох сторін і приберіть позначки `<<<<<<<`, `=======`, `>>>>>>>` |
| `uv.lock` | нічого не правте руками: `uv lock` перерахує його з об'єднаного `pyproject.toml` |
| файл курсу (таблиця нижче) | візьміть версію курсу: `git checkout --theirs <файл>` |

Потім завершіть злиття:

```bash
uv lock                        # якщо конфлікт був у pyproject.toml або uv.lock
git add <файли з конфліктом>
git commit --no-edit
```

Передумали — `git merge --abort` повертає все до стану перед злиттям.

## Чиї файли

| Файли | Чиї | Правило |
| --- | --- | --- |
| `README.md`, `docs/`, `kb/`, `tests/starter/`, `.env.example`, `.gitattributes`, `LICENSE` | курсу | не змінюйте: наступна практична може їх оновити |
| `src/`, `prompts/`, `SPEC.md`, `AI_USAGE_LOG.md`, `tests/` (крім `tests/starter/`), `reports/`, набори для оцінювання і все, що ви створюєте самі | ваші | курс їх не змінює; каркас, що приходить з новою практичною, з цієї миті теж ваш |
| `pyproject.toml`, `uv.lock`, `.gitignore` | спільні | додавайте своє (`uv add <пакет>`); курс дописує сюди залежності нової практичної |

Структуру свого коду можна змінювати: додавати модулі, перейменовувати файли. Сигнатури, позначені в коді як контракт, лишайте: на них спирається наступна практична.

## Умови приймання — для кожної практичної

Робота не перевіряється, доки не виконано всіх умов:

- застосунок і скрипти практичної запускаються з чистого клону однією командою `uv run`, маючи лише `.env` із ключем; залежності при цьому встановлюються точно за закоміченим `uv.lock` — `uv sync --locked` проходить;
- ключа немає ні в коді, ні в історії git;
- `uv run pytest` проходить без мережі — разом із тестами попередніх практичних і тестами в `tests/starter/`;
- в `AI_USAGE_LOG.md` заповнено розділ цієї практичної — журнал використання ШІ.

Перед здачею перевірте себе: `uv lock --check` каже, чи відповідає `uv.lock` файлу `pyproject.toml`, `uv run pytest` — чи проходять тести, а `git status` — чи все закомічено.
